# Pi Observer

A read-only Pi extension that reports one-sentence activity summaries without
adding model tools, context messages, steering messages, or follow-up prompts.

The extension observes Pi lifecycle events and writes short-lived snapshots to
`$PI_OBSERVER_DIR` (default: `<pi-agent-dir>/observer`). Every Pi process that
loads the extension contributes snapshots identified by PID and session ID.
Independently running Pi children and same-process WebUI in-memory subagents
therefore remain distinct in the shared view and report.

## Sandbox startup

Push the sources under `/tmp/ahsb-push/pi-observer/` into a disposable guest.
Its initialization step runs `bash /tmp/ahsb-push/pi-observer/install-guest.sh`
once, before starting Pi. The installer refuses host paths and conflicting
files, and does not change settings, credentials, npm packages or existing VM
bases. Repeating the same installation is safe.

After initialization, ordinary `pi` startup auto-loads the extension from the
guest's agent directory; neither `--extension` nor `/observer` is required.
Independently launched child Pi processes use the same directory automatically
when they inherit the same environment. Processes already running need to be
restarted; `--no-extensions` and different agent directories are not covered.
This is a guest initialization hook, not automatic provisioning of every
sandbox runner or an already-running VM.

The same step installs the standalone plugin into the guest's WebUI data
folder. Open the **Pi Observer** top-level tab in that guest's existing WebUI
and approve read access once to see all instrumented processes together.
The host retains source files only. Use the same `PI_CODING_AGENT_DIR` and,
if overridden, `PI_OBSERVER_DIR` for Pi and the WebUI server.

## Development usage

For a temporary, explicitly loaded development session:

```bash
pi --extension ./observer.ts
```

Run `/observer` for a manual summary. Automatic reports are enabled at a
five-minute interval by default and can be changed with
`PI_OBSERVER_INTERVAL_MINUTES`. Use `/observer off` or `/observer on` to toggle
automatic reports across subsequent tasks. A non-positive interval disables
initial automatic reports; explicit `on` restores the configured positive
interval or the five-minute default. Set `PI_OBSERVER_KEEP_SNAPSHOTS=1`
only when diagnosing cross-process observation; the default removes the
session snapshot and its summary at shutdown.

Each generated summary is also written beside its process snapshot as a
short-lived `*.summary.json` file. This makes the same summary available to a
read-only viewer without changing the observed Pi session. The summary
completion receives only observer snapshots, uses a fresh completion session,
and never writes to the current Pi session or sends a message to the original
model loop. Requests cannot overlap and have a 45-second abort deadline.
A 15-second heartbeat preserves quiet sessions without changing their activity
time; disposed contexts and late SDK events cannot resurrect closed snapshots.

## Web UI tab

`webui/` is a standalone `pi-web-ui` plugin. It adds a **Pi Observer** tab that
shows Pi sessions, distinct process and active-session counts, their latest
observed phase, and the latest summary
from the extension. The plugin does not register agent tools or use chat,
prompt, steering, or shell APIs.

Install the plugin into the `pi-web-ui` data directory that serves your browser:

```bash
pi-web-ui install /absolute/path/to/pi-observer/webui --name pi-observer
```

On first opening the tab, `pi-web-ui` asks for read-only access to the observer
snapshot directory (by default `~/.pi/agent/observer`). The plugin never reads
that directory before approval. When `PI_OBSERVER_DIR` is set for Pi, set the
same environment variable for the `pi-web-ui` server so both processes use the
same directory.

The tab refreshes snapshot state every 15 seconds. It only displays summaries
already generated by the extension, so viewing it neither invokes the observed
agent model nor appends anything to an agent session.

Run the isolated server and client tests from the repository root with:

```bash
node --test pi-observer/observer.test.mjs pi-observer/webui/index.test.mjs pi-observer/webui/client/entry.test.mjs
```

## Disposable guest acceptance

The consumer-owned cases in `tests/sandbox/` declare exact tool versions in
`requires.json`. Sandbox owns runtime preparation, actual CLI/native PTY checks,
`$AHSB_RUNTIME_DIR` and PATH; this project owns guest extension/plugin deployment
and activity/UI assertions. There is no project-specific runtime installer or
preflight shim. Both sides currently share this repository, but their sources
and acceptance responsibilities remain separate.

Prepare the common runtime once with `bin/prepare-tart-runtime.sh <new-base>`
using a private GUI-ready Tart profile, then select that new stopped base.
The preparation uses `image-deps/` and verified npm cache tarballs, installs
inside a separate guest clone, and preserves the original seed. The tests do
not download dependencies or bake Observer into the base. See
[the sandbox consumer contract](../docs/consumer-tests.md).

```bash
# Select a suitable private Tart profile without printing its contents first.
bash bin/test.sh --project "$PWD" macos-observer-autoload
bash bin/test.sh --project "$PWD" macos-observer
bash bin/test.sh --project "$PWD" macos-observer-memory
# In an independently prepared Linux checkout:
EXECUTION=local bash bin/test.sh --project "$PWD" linux-observer-memory
```

The first case checks ordinary Pi startup, two independent active processes,
periodic independent mock-model summaries and shutdown cleanup. The second
requires Aqua and a guest browser, then checks no state before approval, the
permission dialog, both processes, summary text and scheduled refresh. Both
use isolated temporary data directories and a local mock model, with no real
credentials. The memory cases also create a real WebUI persistent parent and
in-memory child using its session APIs, prove distinct snapshots at the same
PID, inspect independent system/user-only summary requests without tools,
and verify complete disposal and shutdown cleanup.

Both guest cases passed on 2026-10-10 in disposable macOS clones: ordinary Pi
auto-loading, two real independent processes, automatic independent mock-model
summary, shutdown cleanup, headed browser read approval, both process states,
summary display and scheduled refresh. The browser DOM assertions and actual
guest desktop screenshot are separate evidence. Runtime versions were Pi
0.87.1, WebUI 0.96.1 and agent-browser 0.38.2 on Node 24.21.0 / ABI 137.

The latest Linux and macOS memory cases also passed, as did the headed macOS
view of five sessions across four processes. Detailed paths, failures and
host Harness repair evidence are in [runtime acceptance](../docs/runtime-acceptance.md).

On 2026-10-12, the Linux `linux-observer-real-provider` case also passed using
`deepseek / deepseek-flash`: two independently generated real summaries matched
the guest's stored reports, with no local fallback and complete shutdown cleanup.
Ordinary fixture agent requests still waited on a mock; only Observer summaries
reached the real provider. A bounded native-credential broker allowed exactly two
requests with no tools or retries, and credentials never entered the guest.

This does not prove macOS real-provider access, observation of uninstrumented Pi,
or default deployment in every sandbox. Real-provider cases require explicit
provider/model and request authorization plus a prepared loopback-only broker
and tunnel; do not run them as an unauthenticated ordinary smoke test.
The broker test checks budget persistence and accepts OpenAI string or text-block
user messages without allowing images or tools. Runtime version probes are
isolated, offline and bounded to 30 seconds.
